# EvoLex 安全与治理设计

> 适用版本：EvoLex 0.3.0  
> 文档定位：当前实现的安全控制、治理语义、部署建议和非保证事项  
> 重要边界：0.3.0 是可运行的参考实现，不是已经通过等保、ISO 27001、SOC 2、HIPAA 或其他行业认证的生产安全产品。

## 1. 安全目标与信任边界

EvoLex 的核心安全目标不是证明抽取内容必然真实，而是确保自动生成的知识变更：

1. 能追溯到明确的来源片段；
2. 在进入 canonical 图谱前保持隔离；
3. 在已声明且可计算的影响域内接受结构约束验证；
4. 只有所有硬门通过且策略允许时才提交；
5. 提交过程在 canonical 注册库内部具备事务性和版本并发校验；
6. 事后能够按版本和贡献生成补偿，而不是覆盖整个当前图；
7. 每次 Agent 决策、工具执行、合并和策略路由可审计。

主要信任边界如下：

```text
不可信输入文档
    │
    ▼
抽取模型边界 ── 可能是本地模型，也可能是外部 API
    │
    ▼
候选与证据区 ── 尚未进入 canonical 图
    │
    ▼
影子图、待排除集合求解与六项 AND 硬门
    │         └─ 因果验证凭证重算
    │
    ▼
canonical 注册库 ── 图版本的事实源
    │
    ▼
单次运行发布库 / 看板 / 下游图系统
```

输入文档、模型输出、外部 Schema 提议和人工配置都应视为可能不完整或恶意；canonical 注册库也不能自动信任来自上游的任意字段，必须依赖校验和策略。

## 2. 证据链

### 2.1 提及与关系端点

联合抽取在每个片段内生成实体提及和关系。关系主客体引用同一响应中声明的 `mention_id`，而不是仅依赖实体名称字符串。

进入全局运行状态前，片段级提及、证据和候选标识会加入片段命名空间，以降低不同片段局部标识碰撞的风险。实体解析产生 `mention_id → entity_id` 映射，关系只有在端点能够映射到规范实体且主客体未因合并坍缩为同一对象时才物化。

未知端点和规范端点坍缩会形成显式失败记录。当前机制提升了错误可见性，但不能保证模型不会漏抽实体或选择错误提及。

### 2.2 证据对象

候选主张至少需要引用一个通过基本字段校验的证据对象。证据对象包含：

- `evidence_id`；
- 来源 `document_id`；
- 来源 `segment_id`；
- 原始证据文本；
- 置信度及运行上下文。

关系规范化时，同一规范关系可以保留多个证据锚点。当前“独立证据”统计以片段级来源为主要边界，不能直接等同于法律或科学意义上的独立来源，也不能证明证据内容本身真实。

### 2.3 合并谱系

实体合并保留原始提及、别名、来源标识和合并决定；关系合并保留原始关系成员、谓词别名、证据和可逆身份假设。类型约束和完整链接条件用于减少传递性过度合并。

这意味着审核员能够查看“哪些对象被合并、依据是什么”，但 0.3.0 不提供对任意历史误合并的自动拆分算法。发现误合并时仍可能需要人工建立补偿或数据修复方案。

### 2.4 补丁证据契约

图演进计划把实体和关系转换为补丁操作，每个操作携带证据契约。契约至少用于表达：

- 操作和对象标识；
- 来源文档、片段和证据标识；
- 证据谱系是否完整；
- 操作声明的影响域；
- 关系端点依赖；
- 置信度和触发 Agent。

canonical 提交后，操作的前态、后态、逆操作和证据契约被写入版本事件。证据链的完整性是可审计结构属性，不是对来源真实性的密码学证明；当前实现也未对原始文档或证据对象做数字签名。

## 3. 候选隔离与发布状态

### 3.1 候选区

抽取出的实体、关系、主张、合并决定和 Agent 轨迹先进入按运行划分的候选注册库。校验失败、证据不足、冲突过高、硬门未通过或 canonical 提交失败的对象不会被当作已发布 canonical 事实。

运行可处于：

- `candidate`：保留供后续评审；
- `quarantined`：因证据、冲突、策略或提交问题隔离；
- `published`：已通过治理路径并形成运行级发布视图。

候选和隔离状态都必须持久化原因，避免“未写入即丢失”导致无法复盘。

### 3.2 canonical 先于运行级发布

Agent 模式中，策略允许发布后，系统仍保持 `candidate` 状态并先执行 canonical 演进提交；只有演化已接受、canonical 提交状态为 `committed` 且发布置信度达标，才允许继续生成运行级发布视图。工具执行许可由控制器按依赖图强制检查，发布节点再独立复核，因此 Agent 提议不能直接构成发布授权。

如果 canonical 提交失败，最终状态降级为隔离；若发布置信度不足，则保持候选。该顺序减少“运行库已发布但 canonical 无版本记录”的风险。

运行级发布库自身使用显式事务：写入实体、关系或运行状态的任一步骤失败即回滚；同一状态按 `run_id` 重试采用快照替换，避免累积重复对象。候选注册库的最终快照同样按运行替换，便于失败后幂等重试。两者目前都没有基于 revision 的 compare-and-swap；若对同一 `run_id` 并发提交内容不同的新旧快照，结果为 last-writer-wins，生产调用方应实施单写者、revision 门或队列串行化。

### 3.3 不存在跨存储全局原子保证

canonical 注册库和每次运行的发布 SQLite 是两个持久化边界。当前没有分布式事务、两阶段提交或 outbox 对账协议，因此：

- canonical 内部提交可以已经成功，而后续运行级发布失败；
- 候选注册库、检查点、Schema 库和 canonical 库之间不存在一个覆盖全部存储的原子事务；
- 生产化时应把 canonical 版本作为事实源，为派生发布增加幂等键、重试队列、对账任务和告警。

任何对外材料都不应把当前实现描述为“跨存储原子发布”。

## 4. 影子验证

### 4.1 影响域生成

影子验证不会默认比较整图的所有可能语义。系统从以下信息合并声明影响域：

- 补丁操作中的实体和关系标识；
- 证据契约中的文档、片段和证据标识；
- 关系的主客体依赖；
- 基线图中与受影响端点或谓词的一跳关联。

影响域会记录其依据并计算内容摘要。完整候选补丁派生的原始影响域在全部反事实和排除集合重放中冻结；接受操作自身较小的声明域只能作为记录，不替换域外投影边界。该方法用于降低遗漏直接依赖的概率，但不保证覆盖未知的跨图业务规则、应用缓存、外部索引或多跳语义影响。

### 4.2 自动不变量

补丁应用到基线快照时，系统生成并执行结构不变量，例如：

- 新增或更新的规范实体存在；
- 关系主客体在影子图中均可解析；
- 规范关系键保持唯一；
- 补丁应用后没有违反已生成的端点约束。

领域业务规则仍需由客户提供。例如“某设备在同一时刻只能属于一个产线”或“某法规义务必须有生效日期”并不能仅由通用结构不变量推出。

### 4.3 确定性回放

同一补丁对同一基线执行两次，系统比较规范化快照哈希。哈希一致用于验证补丁应用逻辑在当前进程中的确定性。

该检查不证明：

- 上游 LLM 对同一文本每次都会生成相同补丁；
- 外部 API 调用具备 exactly-once 语义；
- 不同代码版本、不同排序规则或不同存储实现会产生相同结果。

生产回放应同时固定 EvoLex 版本、模型、提示词、Schema、策略、输入文档和基线图版本。

### 4.4 非干扰检查

系统从基线快照和影子快照中移除冻结的原始影响域对象，对剩余投影计算哈希并比较。相同表示在当前投影定义下，补丁未改变影响域外的实体和关系结构。

这一检查不是形式化证明，也不等价于“任意业务查询的结果不变”。以下变化可能不在当前检查覆盖范围内：

- 下游自定义查询的聚合或排序变化；
- 多跳路径、推理规则或图算法结果变化；
- 外部向量索引、缓存和物化视图变化；
- 业务系统对置信度、证据数量或时间的隐式解释。

高风险场景应将客户关键查询加入显式回归套件。

## 5. 反事实排除求解与历史补偿

### 5.1 提交前反事实原因与待排除集合

若影子查询失败，系统先取得与查询静态关联的操作。对每个操作，以该操作及实体—关系端点依赖闭包作为排除集合，从同一基线在冻结影响域下重放；只有目标查询不再失败时才把该操作确认为反事实原因操作。

候选数不超过 16 时，当前实现在已验证反事实原因及其依赖闭包所定义的搜索空间内枚举排除组合，选择能够同时满足不变量和非干扰要求的最低成本方案。成本由被排除操作数量、影响范围、证据损失及置信度保留共同决定，并在报告中提供求解模式和最优性信息；“精确”仅指该定义搜索空间内的枚举，不外推到任意候选操作空间。

候选数超过16时，系统从完整原因闭包开始重复单项删除和重放直至固定点，并标记为单删除局部最小、非全局结果。不能声称全局最小或一般集合包含极小。对于大型补丁，建议：

- 按文档、子图或依赖连通分量拆分；
- 接入整数规划、SAT/SMT 或其他可证明优化器；
- 对高风险回退要求人工批准。

### 5.2 提交后的选择性补偿回滚

canonical 回滚创建新的补偿版本，而不是删除目标版本或恢复旧数据库快照。系统逆序读取目标版本事件，并对仍可安全归因的操作生成补偿：

- 删除仅由目标版本新增且未被后续版本更新的别名或提及；
- 删除仅由目标版本新增的关系证据；
- 若对象仍有其他版本贡献、剩余证据或活跃关系，则保留对象；
- 对不能安全补偿的操作跳过并记录。

该设计的目标是保留后续贡献和完整历史。它不承诺自动恢复所有业务状态，也不提供任意实体簇的自动拆分。补偿后仍应执行一致性检查和下游对账。

## 6. 基础硬门、因果验证凭证和提交选择

剩余子补丁只有在六个硬条件全部满足时才被接受：

| 检查角色 | 硬条件 | 失败处理 |
|---|---|---|
| EvidenceContractAgent | 所有接受操作证据谱系完整，且影响域有证据依据 | `hold` |
| DeterministicReplayAgent | 同基线同补丁重复回放哈希一致 | `hold` |
| NonInterferenceAgent | 当前定义的非影响域投影一致 | `hold` |
| InvariantAgent | 剩余子补丁重放后的影子不变量全部通过 | `hold` |
| UtilityAgent | 质量—风险效用不为负 | `hold` |
| CausalCertificateAgent | 基线、影响域、查询原因、求解器、排除/接受操作、最终影子及门结果重算一致 | `hold` |

结果对象记录的`required_quorum`为5，但当前接受条件显式要求上述六个布尔条件全部为真，因此 quorum 只能作为冗余审计统计，不能覆盖任一硬条件失败。验证节点生成凭证后，判定节点重算凭证；提交执行节点再重算一次，并要求 decision、evaluation 和 certificate 三方的接受操作标识一致。规范图存储最后计算并核对包含 patch、parent、实际接受操作摘要和凭证ID的提交清单。任一阶段不一致均不得推进活动版本。若未来修改法定人数逻辑，应将硬否决项和可投票项分开配置。

这些Agent是逻辑检查角色，不代表独立组织或统计独立模型。凭证是内容寻址一致性清单，不是数字签名；能够同时修改内容和摘要的对手需要HMAC、签名或不可变日志。关键高风险提交仍应配置人工批准。

## 7. canonical 原子提交

### 7.1 canonical 注册库内部保证

canonical 提交在一个 SQLite `BEGIN IMMEDIATE` 事务内执行：

1. 以`patch_id`查找重复候选，并核对包含父版本、接受操作ID及内容摘要、凭证ID的提交清单；只有清单一致才返回幂等结果；
2. 比较补丁计划的 `parent_version_id` 与当前活动版本，拒绝陈旧父版本；
3. 创建图版本记录并持久化接受操作、凭证ID和提交清单摘要；
4. 应用接受的实体和关系操作；
5. 写入别名、提及和关系证据；
6. 为每个操作记录前态、后态、逆操作、证据契约和触发者；
7. 更新活动图版本指针；
8. 任一步骤异常则回滚该 canonical 事务。

SQLite 启用 WAL 和外键检查。父版本校验防止两个基于同一旧基线规划的补丁静默覆盖；冲突补丁需要在最新基线上重新规划和验证。

### 7.2 能力边界

该事务不覆盖：

- 外部模型 API；
- 候选注册库；
- Schema 候选库；
- 检查点库；
- 运行级发布库；
- 外部图数据库、搜索索引或消息系统。

生产连接器必须定义提交后的幂等传播、失败重试、状态对账和补偿协议。仅依赖本地 SQLite 成功返回不足以声明端到端 exactly-once。

## 8. Schema 并发升级与版本固定

### 8.1 运行时固定

每次运行启动时读取活动 Schema，并把完整活动版本和 `schema_version` 写入运行状态。后续 Schema 差距检测使用该固定快照，而不是每个节点重新读取全局活动版本。

因此，另一个任务在运行中晋升新 Schema，不会改变本次任务已经固定的类型、谓词和属性集合。本次输出应始终记录所用 Schema 版本。

### 8.2 Schema 晋升

Schema 提议先作为候选积累出现次数、文档来源、证据覆盖和一致性指标。晋升操作在 Schema SQLite 存储的 `BEGIN IMMEDIATE` 事务中：

- 读取当前活动版本；
- 校验提议仍为候选；
- 拒绝空版本、当前活动版本或已存在的目标版本；
- 基于活动版本创建带父指针的新版本；
- 记录晋升事件；
- 更新活动 Schema 指针。

SQLite 写锁可以串行化本地晋升事务，但不构成跨节点分布式锁。`activate_schema_version` 这类管理操作也需要在生产环境外包统一的授权、并发控制和审计。

### 8.3 Schema 风险控制

- 新类型、关系和属性不能仅凭单次模型输出自动进入正式 Schema；
- Schema 提议重放应保持幂等，避免同一运行重复累加支持数；
- Schema 晋升后应使用冻结语料和关键业务查询做回归；
- 已固定旧 Schema 的运行可以完成，但其结果与新 Schema 的兼容性需在后续变更中处理；
- 0.3.0 不实现自动 Schema 迁移、跨版本数据重写或向后兼容证明。

## 9. Agent 工具依赖与状态新鲜度

Agent 可因证据不足或风险判断重新执行上游工具。若只记录“工具曾完成”而继续复用旧下游结果，会出现典型陈旧状态问题：重新抽取后仍沿用旧实体解析、旧关系或旧影子报告。

0.3.0 为工具建立依赖图。上游工具重跑时：

- 标记所有已计算后继工具失效；
- 清理后继工具产生的状态字段；
- 增加当前工具修订号；
- 在 Agent 轨迹中记录被失效的工具；
- 要求后续步骤基于新状态重新执行。

该机制覆盖 EvoLex 内建工具依赖。自定义插件或外部副作用若未声明依赖，不会自动获得相同保证。

## 10. Checkpoint、恢复与回放

### 10.1 当前能力

每个节点或 Agent 工具完成后，系统可把完整 `GraphState`、运行标识、线程标识、节点名和单调步骤号保存到 SQLite 检查点库。

- `latest_for_thread` 按最新插入记录选择恢复点，避免旧运行中较大的步骤号遮蔽新运行；
- Agent 恢复继承检查点步骤号并继续递增；
- `replay_run` 可以按步骤查看状态、策略决定和警告变化；
- 确定性流水线和 Agent 流水线分别使用相应恢复路径。

### 10.2 恢复边界

检查点是状态恢复机制，不等于事务日志：

- 检查点可能包含原始文本、证据和模型结果，是高敏感数据；
- 不能撤销检查点之前已经发生的外部 API 调用；
- 恢复后模型调用可能返回不同结果；
- 若上一个工具已产生外部副作用但检查点未写入，仍可能重复执行；
- 本地 SQLite 损坏或磁盘丢失时没有内建远程灾备。

生产部署需要检查点加密、备份、保留策略、幂等外部调用和恢复演练。

## 11. 数据隐私与部署模式

### 11.1 可选部署模式

| 模式 | 文本是否离开部署环境 | 当前特点 | 适用边界 |
|---|---|---|---|
| 显式离线模式 `EVOLEX_OFFLINE=1` | 否 | 使用本地启发式抽取，便于测试和无网络演示 | 不应假设具有生产级抽取质量 |
| 本地 OpenAI 兼容端点 | 取决于端点部署位置 | 可指向 localhost，允许本地兼容服务使用占位密钥 | 需自行保障模型服务、日志和网络安全 |
| 外部 OpenAI 兼容 / DeepSeek API | 是 | 文本片段发送到所配置提供方 | 必须经过数据分类、合同、地域和保留政策评审 |

默认配置指向 DeepSeek 兼容端点，但无密钥时不会静默发送请求；显式离线模式与本地端点可用于数据不出域场景。

### 11.2 本地持久化敏感面

以下文件可能包含原文、证据、实体关系、Agent 轨迹或策略信息：

- candidate registry SQLite；
- canonical registry SQLite 及 WAL 文件；
- Schema candidate SQLite；
- checkpoint SQLite；
- 单次运行发布 SQLite；
- `visualize`单页以及`visualize-bundle`生成的自包含可视化 HTML；
- 评测 JSON / Markdown 报告。

`visualize-bundle`输出`index.html`、`evolex-global-kg.html`和`documents/evolex-doc-*.html`。所有图页面都把数据、样式和交互脚本嵌入HTML，不调用CDN或后端API；白底严肃风格和无需网络只降低部署依赖，并不降低数据敏感度。

单文档页面以`entity_mentions.document_id`和`relation_evidence.document_id`作为直接隔离边界，并仅补齐已选关系的端点。共享canonical实体不会自动扩张仅由其他文档支持的关系或证据；但该投影是展示层数据最小化，不是租户授权、行级安全或密码学隔离。`document_id`是内容快照标识，不是文件名、人员身份或访问控制主体。导出文件名使用安全化片段和摘要，不能直接把未经处理的`document_id`解释为路径。

自包含看板会把原文证据、实体关系、Agent轨迹、凭证和版本记录写入可复制的HTML。不能因为它“只是静态文件”或某个逐文档页面对象较少就公开分发；整个bundle及其单独页面都属于敏感导出物，应使用与生产数据相同的访问控制、加密、留存、下载审计和销毁策略。

### 11.3 密钥管理

LLM 配置可从环境变量、命令行或本地配置文件读取。当前 `save_llm_config` 在用户配置文件中以明文保存 API 密钥，错误日志仅对常见 Bearer 令牌模式做脱敏。

生产环境建议：

- 不把密钥写入仓库、命令历史、看板或检查点；
- 优先使用密钥管理服务、短期令牌或受控环境注入；
- 限制本地配置文件权限，并避免使用当前明文持久化方式；
- 对日志做结构化脱敏，覆盖提供方返回体和异常链；
- 轮换密钥并监测异常调用。

### 11.4 生产隐私控制清单

- 在入模前做 PII、商业秘密和受监管数据分类；
- 对无需原文的场景进行最小化、脱敏或字段屏蔽；
- 为外部模型提供方确认数据驻留、训练使用、日志保留和删除条款；
- 全链路 TLS，私有部署使用网络白名单或 mTLS；
- 本地数据库和备份启用静态加密；
- 按租户隔离数据库、目录、密钥和访问角色；
- 为候选、检查点、证据和看板设置独立保留期限；
- 提供删除请求和证据撤回后的级联处置流程；
- 对读取证据、批准补丁、晋升 Schema 和回滚设置最小权限；
- 定期审计导出文件和临时目录，避免静态看板成为泄露通道。

0.3.0 尚未内建字段级加密、企业 RBAC、租户隔离、保留期自动执行、数据主体删除工作流或审计日志签名。

## 12. 威胁与缓解

| 威胁 | 可能影响 | 0.3.0 控制 | 生产化补充 |
|---|---|---|---|
| 文档提示注入 | 模型受文档中指令影响，输出错误关系 | 结构化输出、端点和证据校验、候选隔离 | 内容/指令分离、模型网关、谓词白名单、对抗测试 |
| 模型幻觉或漏抽 | 错误或缺失知识 | 证据引用、置信度、硬门、影子结构检查 | 金标回归、人工审批、模型集成比较 |
| 错误同类合并 | 多条关系被错误折叠 | 类型约束、完整链接、合并谱系 | 领域阻断规则、人工复核、拆分工具 |
| 恶意或陈旧补丁 | 覆盖新版本状态或复用错配版本 | 父版本、因果验证凭证、三方选择一致和提交清单 | 身份认证、签名、审批、重放窗口限制 |
| 绕过候选区直接写库 | 未验证知识进入生产 | Agent 路径要求 canonical 提交后发布 | 数据库权限隔离、服务端唯一写入口 |
| 检查点或看板泄露 | 原文和证据外泄 | 本地文件边界 | 加密、RBAC、保留与下载审计 |
| 大补丁拒绝服务 | 待排除集合搜索空间增长 | 精确阈值和回退策略 | 配额、分区、超时、外部优化器 |
| SQLite 单点故障 | 数据不可用或并发受限 | WAL、本地事务 | 备份、复制、受支持的生产数据库 |
| 多存储部分成功 | canonical 与派生视图不一致 | canonical 先提交 | outbox、幂等消费者、对账和告警 |
| 管理员误晋升 Schema | 运行语义变化 | 候选状态、版本记录、运行固定 | 双人审批、权限分离、回归门禁 |

## 13. 运维治理建议

### 13.1 角色分离

生产环境至少应区分：

- 数据接入者：提交文档，不得批准高风险补丁；
- 知识审核者：查看证据和合并决定；
- Schema 管理者：批准类型、谓词和属性演进；
- 发布管理员：管理策略和生产连接器；
- 安全审计者：只读访问版本、事件、日志和配置变更；
- 系统管理员：管理基础设施，但不默认读取业务证据。

0.3.0 尚未实现这些角色，当前需要依赖操作系统文件权限和部署流程隔离。

### 13.2 关键告警

- canonical 提交失败或父版本陈旧；
- canonical 已提交但运行级发布未完成；
- 六项任一硬门或凭证重算失败；
- 冻结原始影响域摘要变化或域外投影哈希不一致；
- 大补丁进入单删除局部、非全局回退模式；
- 证据覆盖或端点有效率低于客户阈值；
- Schema 晋升、回退或手工激活；
- 回滚存在跳过操作；
- 检查点、数据库或看板异常增长；
- 外部模型调用量、错误率或数据地域异常。

### 13.3 备份与恢复

- 对 canonical、Schema、候选和检查点库分别制定恢复点和恢复时间目标；
- 备份 SQLite 主文件时同时考虑 WAL 一致性，优先使用 SQLite 在线备份机制或停写快照；
- 定期执行“从备份恢复—重放—下游对账”演练；
- 保留图版本和事件，但根据隐私要求对原始证据实施可执行的保留与删除策略；
- 在迁移到外部图数据库前，验证 canonical 版本到下游对象的幂等映射。

## 14. 明确的非保证事项

EvoLex 0.3.0 不保证：

- 抽取结果、证据文本或来源文档必然真实；
- 实体和关系联合抽取后不再漏抽或误抽；
- 同类实体/关系合并永远正确；
- 自动拆分任意已误合并对象；
- 影子哈希证明所有业务语义、查询结果或下游系统完全不变；
- 超过精确求解阈值的待排除集合是全局最优或一般集合包含极小；
- 内容寻址凭证提供数字签名、身份认证、对抗性不可篡改或知识真实性证明；
- canonical、候选、Schema、检查点、运行发布和外部图系统跨存储原子；
- 外部模型调用 exactly-once 或可确定性重放；
- 系统会从生产反馈中自动在线学习；
- SQLite 参考实现具备企业级高可用、多租户和无限水平扩展能力；
- 当前本地文件、密钥配置和看板已经满足企业加密、RBAC 或合规认证要求；
- 仅凭自动硬门即可替代高风险领域的专家、合规或法律审批。

安全表述应始终以“已实现的控制及其验证范围”为依据。EvoLex 的核心治理价值在于让知识变更更可见、可检验、可隔离和可补偿，而不是消除所有模型、数据和业务风险。
