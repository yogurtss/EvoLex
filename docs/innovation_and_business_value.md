# EvoLex 创新点与商业价值（第二轮严格审查版）

## 1. 一句话定位

> EvoLex是知识图谱变更控制面：位于文档/模型/人工变更源与生产图数据库之间，在固定来源边界内验证候选图补丁、反事实定位失败操作、局部保留可行知识，并用内容寻址凭证和提交清单防止验证结果与实际版本事件错配。

它不是“另一个三元组抽取器”。抽取模型可替换，控制协议、审计记录和版本治理才是长期产品价值。

## 2. 客户为什么需要它

### 2.1 LLM输出不能直接写入生产KG

模型可能产生悬空端点、来源缺失、重复关系、限定信息丢失或schema冲突。人工逐条复核成本随文档和版本增长，普通置信度阈值又不能说明具体失败由哪个操作触发。

### 2.2 一条坏操作导致整批拒绝

批次级all-or-nothing门控会同时丢弃同批次中正确实体和关系。生产团队需要只排除导致约束失败的候选操作，同时保留其余可验证知识。

### 2.3 验证通过不代表提交内容相同

在多节点工作流、重试和并发中，评估集合、判定集合和提交集合可能不一致。只记录日志或完整patch ID无法阻止同一候选patch在不同接受选择下命中旧版本。

### 2.4 审计资料散落

来源、影响范围、结构查询、失败原因、排除集合、Agent轨迹、实际写入事件和版本回滚常分散在不同系统，难以形成一份可复核证据包。

## 3. 严格创新分级

### A级：核心专利与产品壁垒

#### 3.1 冻结来源约束影响域

候选操作携带来源锚、声明影响对象和关系端点依赖。系统结合父版本基线一跳邻接形成原始影响域并计算摘要。之后即使局部排除操作，全部反事实和求解重放仍使用原始域。

技术效果：防止repair过程中验证边界同步缩小，使原候选补丁曾触及的对象仍位于非干扰检查边界内。

#### 3.2 依赖闭包反事实原因验证

失败查询初始只有操作关联。系统逐个排除关联操作及依赖其实体端点的关系操作，从同一基线重放；目标失败消失时才认定该排除种子为反事实原因候选。

技术效果：把“标签式归因”转化为可执行重放记录，减少无关操作进入排除求解空间。

边界：这是候选补丁范围内的操作原因定义，不是现实世界或统计因果。

#### 3.3 内容寻址因果验证凭证

凭证绑定：

- 父版本和基线摘要；
- 完整候选操作摘要；
- 原始/冻结/接受操作声明域摘要；
- 查询关联、反事实原因和检查记录；
- 求解模式、性质及结果；
- 排除/接受操作；
- 最终影子摘要和门结果。

判定和提交阶段都重算完整凭证。任何绑定字段变化都会使核对失败。

技术效果：检测验证内容、基线、原因、求解器或选择在工作流节点间被替换。

边界：内容摘要不是数字签名；对抗性身份认证需要额外HMAC、签名或不可变日志。

#### 3.4 实际接受操作绑定的提交清单

存储层持久化完整patch ID、父版本、排序接受ID、接受操作内容摘要、凭证ID和提交清单摘要。相同patch ID只有清单完全一致才作为幂等重放；不同接受集合或凭证被拒绝。

技术效果：避免“本次凭证对应集合B，但存储返回首次集合A版本”的重试错配。

### B级：重要回退与产品能力

#### 3.5 局部排除和剩余子补丁

求解器在反事实原因及KG端点依赖闭包内选择待排除集合。小空间精确枚举；大空间固定点单删除回退并明确标记非全局性质。

商业效果：提高有效知识保留率，减少人工重新抽取和整批回滚。

#### 3.6 同批次实体—关系—证据端点

关系候选引用同批次mention ID；证据先过滤，再校验关系引用；只有零条有效联合关系成功物化时才进行关系回退。

商业效果：降低未解析端点和模型二次调用成本。

#### 3.7 同类实体和限定关系规范化

实体合并要求same-type、来源完整和跨簇任意成员对满足阈值。关系身份加入限定信息摘要，并保存逐条源断言快照。

商业效果：减少传递性过合并和不同时间/条件事实误合并，便于审计与恢复。

#### 3.8 contribution/tombstone历史补偿

回滚创建追加版本，按剩余贡献、较后墓碑和新生命周期重算；不安全事件跳过并记录。

商业效果：避免恢复旧快照覆盖后续正确状态。

### C级：说明书或商业秘密

- noisy-OR和置信度上限；
- Agent EIG调度；
- 普通发布评分；
- schema提议和晋升；
- 全局活动图与逐文档来源投影的自包含HTML可视化；
- 别名词典、阈值、客户规则和模型路由。

这些能力有产品价值，但现有技术拥挤或易替换，不应宣传为核心专利点。其中双层静态HTML无需部署前后端即可用于受限网络环境交付和客户验收；逐文档投影可缩小人工证据复核范围，总图可提供跨来源活动对象概览。上述价值来自部署与审计路径缩短，不表示可视化本身提高抽取准确率或形成创造性。

## 4. 产品架构

```text
文档 / LLM / ETL / 人工变更
              │
              ▼
      Candidate Patch Adapter
              │
              ▼
  Source-bound Impact Domain Builder
              │ frozen domain hash
              ▼
       Shadow Constraint Runner
              │ failed queries + associated ops
              ▼
 Counterfactual Attribution & Repair Solver
              │ excluded set + residual subpatch
              ▼
  Causal Validation Certificate Service
              │ verified accepted operations
              ▼
 Commit Manifest & Canonical Version Store
              │
       ┌──────┴──────┐
       ▼             ▼
 Production KG   Audit Evidence Pack
```

上游可使用EvoLex联合抽取器，也可接入外部抽取、人工编辑或其他图变更源。这样商业覆盖面不被某个模型供应商限制。

## 5. 产品形态

### 5.1 KG Change Control Gateway

以API/SDK形式接收候选patch，输出：

- `accepted`、`held`或`quarantined`；
- 原始影响域；
- 结构查询和反事实检查；
- 待排除集合和剩余子补丁；
- 因果验证凭证；
- 图版本及提交清单。

### 5.2 Managed Governance Service

托管影子执行、规则版本、凭证、审批、审计与图数据库连接器，按文档量、patch量或图版本计费。

### 5.3 Compliance Evidence Pack

按`run_id + graph_version_id + operation_id`导出来源、查询、反事实检查、排除集合、凭证和提交清单，用于内部审计、模型风险管理、质量体系或客户验收。

### 5.4 Domain Editions

- 科研情报：论文、专利和实验事实；
- 制造：设备、部件、工艺和故障关系；
- IT运维：服务依赖、告警、变更和故障传播；
- 医药/法规：适应证、义务、控制项和版本证据；
- 企业数据目录：数据资产、责任人、血缘和质量规则。

## 6. 与常见方案的差异

| 方案 | 擅长 | 缺口 | EvoLex补充 |
|---|---|---|---|
| 纯LLM三元组抽取 | 快速生成 | 端点、来源、版本和错误隔离弱 | 同批次端点及变更控制面 |
| 向量RAG | 语义检索 | 无稳定图身份和patch事务 | 规范身份、来源和版本事件 |
| 图数据库 | 存储和查询 | 不解释候选变更为何安全 | 提交前冻结域、反事实和凭证 |
| MDM/实体解析 | 实体身份 | 关系限定信息和图补丁治理不足 | 双层身份及源断言快照 |
| 数据质量/SHACL | 约束验证 | 往往输出violations，不绑定局部保留和实际提交 | 原因候选、剩余子补丁和清单 |
| 普通Agent workflow | 灵活编排 | 结果可能不可审计或错配 | 数据依赖、双重凭证核对和幂等清单 |
| event sourcing | 历史事件 | 不决定未提交KG候选的来源边界和原因 | 提交前控制 + 贡献级历史补偿 |

## 7. 可量化ROI

| 指标 | 定义 | 商业价值 |
|---|---|---|
| Valid operation retention | 错误批次中最终保留的正确操作/正确操作总数 | 降低整批返工 |
| Endpoint resolution rate | 联合关系中成功解析两个端点的比例 | 提高构图产出 |
| Evidence-reference validity | 进入物化的关系候选中证据引用有效率 | 降低无来源知识 |
| Impact-domain reduction | 局部域读取对象数相对全图读取对象数降低 | 降低验证成本 |
| Root-cause precision/recall | 反事实原因与注入真值比较 | 降低人工定位时间 |
| Certificate tamper detection | 注入错配被阻断比例 | 提升控制可靠性 |
| Conflicting retry rejection | 同patch不同selection重试拒绝比例 | 避免版本错配 |
| Audit lead time | 从告警到定位来源/操作/版本的时间 | 降低审计和运维成本 |
| Later-state preservation | 历史补偿后正确保留的后续贡献比例 | 降低恢复副作用 |

## 8. 商业模式

可组合：

- 开源核心 + 企业连接器/治理包；
- 按年订阅的私有部署；
- 按patch或文档量计费的托管API；
- 审计、规则建模和行业schema专业服务；
- 生产支持、SLA和长期版本维护。

定价应基于可验证价值：减少人工复核工时、降低错误写图事故、提高有效知识保留和缩短审计周期，而不是按“Agent数量”定价。

## 9. 建议市场切入

优先选择：

1. 已经有图数据库或GraphRAG，但不敢自动写图的团队；
2. 文档持续更新且要求来源审计的行业；
3. 经常因一条坏关系回滚整批数据的团队；
4. 需要证明“本次模型输出实际写了什么”的模型治理场景。

首个试点不应追求开放域抽取SOTA，而应选择可定义结构约束和故障注入真值的窄域，以证明控制面ROI。

## 10. 90天商业验证路线

### 0—30天：可重复控制实验

- 冻结公开数据集和故障注入集；
- 比较分步/联合端点；
- 测量冻结域效率和局部保留率；
- 完成凭证/清单篡改矩阵；
- 生成一份客户可读Evidence Pack。

### 31—60天：连接器与试点

- 完成一个主流图数据库连接器；
- 定义客户结构规则和来源字段；
- shadow-only运行，不自动写生产；
- 与客户人工审核结果对比原因和保留集合。

### 61—90天：受控发布

- 低风险patch自动提交，高风险保持审批；
- 持续对账canonical版本与生产图；
- 量化人工时长、事故率和知识保留率；
- 形成专利实验补充和商业案例。

## 11. 商业与技术风险

| 风险 | 影响 | 控制 |
|---|---|---|
| 数据库repair现有技术强 | 专利创造性挑战 | 锁定冻结来源域、反事实端点闭包、凭证和提交清单耦合 |
| 内容摘要无密钥 | 对抗者可重算 | 生产增加HMAC/签名/不可变日志 |
| 结构域不等于业务语义 | 可能漏检外部副作用 | 客户规则、外部索引对账、canary和shadow-only |
| 大候选空间求解成本 | 延迟/DoS | 分区、配额、超时、外部ILP/SAT及诚实性质标记 |
| 自动抽取准确率不稳定 | 上游噪声 | 模型可替换、证据门、领域校准和人工审批 |
| 多run治理详情仅绑定最新相关registry | 跨运行联合审计信息不完整 | 增加显式run/version/operation复合索引；不得依赖文件时间推断 |
| 专利公开泄露参数 | 商业秘密损失 | 只公开充分实施所需内容，客户词典/阈值/规则保密 |

## 12. 不夸大的对外表述

推荐：

> “EvoLex在KG写入前冻结来源约束验证边界，通过反事实重放局部保留可行操作，并用内容寻址凭证和提交清单确保验证选择与实际版本一致。”

避免：

- “首次用Agent实现自进化知识图谱”；
- “保证知识真实”；
- “不可篡改凭证”；
- “求得全局最优修复”；
- “任何错误都能自动修复”；
- “已经达到开放域SOTA”。

## 13. 组合式知识产权壁垒

- 主专利：冻结来源域、反事实局部排除、凭证和提交清单；
- 分案：联合端点/双层身份；contribution/tombstone历史补偿；
- 软件著作权：源码、控制台和文档；
- 商业秘密：阈值、别名词典、客户规则、提示、性能参数和部署拓扑；
- 商标：EvoLex及商业产品名；
- 数据资产：故障注入集、客户验证集和审计基准。

真正可持续的壁垒是“专利保护的协议 + 可运行实现 + 故障数据 + 企业连接器 + 审计工作流”，而不是某个单一模型或Agent角色。
