1. 执行摘要

该系统面向半导体领域文档，不依赖预先存在的用户问题，也不要求人工逐条标注。文档本身是驱动力：系统持续分析语料、提取知识、发现 Schema 缺口，并在受控条件下演化本体和图谱。

核心边界：LangGraph 负责流程、状态与权限；Agent 负责语义判断；Validator 负责硬校验；Policy Engine 负责治理决策；Publisher 是唯一能写生产知识和生产 Schema 的组件。
1

单一状态真源

LangGraph Checkpointer 保存执行状态，不再引入第二套工作流引擎。

2

双循环

知识生产循环与 Schema 演化循环分离，彼此反馈但不互相直接污染。

3

三道门禁

结构化校验、语义复核、Policy Engine 决策后才允许发布。

PART I

整体思路与系统架构

聚焦系统为什么这样设计、Agent 如何驱动、各层如何协作，以及如何在自动化条件下保持可控。

2. 问题定义与系统目标

2.1 要解决的问题

  • 半导体文档数量持续增长，类型包含论文、专利、技术手册、标准、设备资料、故障记录和行业报告。
  • 不存在预先定义的用户问题，系统必须主动理解语料、发现主题和管理知识。
  • 不希望逐条人工标注实体、关系和本体，但需要长期保持一致性、可追溯性和可回滚性。
  • 半导体知识高度条件化，普通三元组难以表达工艺参数、材料、设备、环境和测量结果。

2.2 明确不采用的方式

不采用自由多 Agent 社会

不让多个 Agent 长期自主聊天、无限反思或自行修改生产图谱。

不采用“LLM 一次生成完整本体”

本体从跨文档实例与关系模式中逐步归纳，并经过版本化治理。

不将 Agent 作为数据库客户端

Agent 不获得任意 SQL、Cypher 或文件系统写权限，只调用白名单工具。

不只存裸三元组

以 Claim、Condition、Measurement、Evidence 和 Provenance 为核心对象。

2.3 最小元模型

无需人工定义全部半导体领域类，但建议固定一个小型 Meta-schema，保证不同批次输出可兼容：

DocumentEvidenceMention EntityConceptProcess EventClaimCondition MeasurementRelationAttribute

3. Agent 如何驱动系统

这里的“Agent 驱动”不是由用户对话驱动，而是由文档和知识状态变化驱动。 Agent 的自主性体现在选择语义动作，而不是获得整个系统的控制权。

文档新增 / 更新
→
LangGraph 创建运行
→
Agent 判断文档与语义
→
工具检索与候选生成
→
验证与策略门禁
→
候选积累 / 正式发布

4.1 三类驱动事件

数据事件

新文档、版本变化、来源变更、删除或定时重处理。

知识事件

无法归类术语、实体冲突、重复实体、新关系模式或证据矛盾。

治理事件

Schema 候选达到阈值、类型膨胀、质量下降、模型或 Prompt 版本升级。

4. 总体系统架构

① Trigger & Control Plane — LangGraph 文档事件、线程 ID、运行状态、节点路由、检查点、预算、重试、interrupt、回放
② Bounded Semantic Agents Corpus Analyst、Semantic Extractor、Entity Resolver、Schema Proposer、Semantic Critic
③ Deterministic Validation & Policy JSON/Pydantic、证据跨度、单位、逻辑循环、Domain/Range、风险级别、自动发布策略
④ Knowledge Lifecycle & Storage Raw Document → Mention → Candidate → Validated → Production；Schema Candidate → Shadow → Published

5.1 两个相互反馈的主循环

Knowledge Production Loop

文档解析 → 语义原子 → 实体解析 → Claim 规范化 → 证据校验 → 知识发布。

Schema Evolution Loop

Schema Gap → 候选类型/关系 → 跨文档积累 → Shadow 评估 → Schema 版本发布。

两个循环共享候选与证据信号，但使用不同的发布策略。普通知识实例可以快速发布， Schema 结构变更必须经过更严格的影子迁移和回归测试。

5. 本体与知识治理

9.1 知识生命周期

OBSERVED
  → EXTRACTED
  → NORMALIZED
  → RESOLVED
  → EVIDENCE_VERIFIED
  → CRITIC_APPROVED
  → CANDIDATE
  → PUBLISHED

异常路径：
NEEDS_MORE_EVIDENCE / AMBIGUOUS / QUARANTINED / REJECTED

9.2 Schema 生命周期

OBSERVED
  → CANDIDATE
  → STABLE_CANDIDATE
  → SHADOW
  → CANARY
  → PUBLISHED
  → DEPRECATED

9.3 风险分级

等级变更策略
低风险 新实例、新 Claim、新证据、别名补充 门槛通过后自动发布
中风险 新类型、新关系、新属性、Domain/Range 扩展 稳定候选 + 独立 Critic + Shadow
高风险 正式类型合并/拆分、父类变化、删除、历史批量迁移 影响分析 + Shadow Migration + Canary + 可回滚

9.4 自动晋升信号

  • 独立支持文档数与来源多样性。
  • 术语语境稳定性、实例聚类一致性和关系模式一致性。
  • 与已有 Schema 的相似度及可分离性。
  • 证据覆盖率、冲突率、时间稳定性。
  • Frozen Corpus 上的新旧版本质量差异。

6. 可控 Harness 设计

10.1 LangGraph 负责的控制能力

状态

共享 State、Checkpoints、线程历史、恢复与回放。

路由

条件边、重试路径、隔离路径、Shadow 和发布路径。

预算

模型调用、工具调用、Token、时间与最大循环次数。

权限

节点级工具白名单、只读/候选写/生产写分离。

版本

模型、Prompt、Schema、Policy、工具与图拓扑版本。

审计

每个状态变化、工具调用、验证结论和发布原因可追踪。

10.2 工具网关

Agent 不直接访问底层存储，仅可调用窄接口工具：

search_entity_candidates(...)
search_schema_candidates(...)
read_evidence(...)
get_relation_patterns(...)
normalize_measurement(...)
submit_entity_candidate(...)
submit_schema_proposal(...)
mark_conflict(...)

10.3 硬停止条件

  • 每个节点最大重试次数。
  • 每次运行最大 LLM 和工具调用数。
  • 每个实体解析最大候选数和上下文扩展次数。
  • 达到预算仍不确定时，必须输出 AMBIGUOUS 或 UNKNOWN。
  • 单次运行最多提出有限数量 Schema 变更，防止本体爆炸。

10.4 持久化与中断

编译图时使用数据库支持的 Checkpointer。LangGraph 会将状态按线程保存为检查点， 可支持故障恢复和 time-travel 调试。[2] 高风险节点可调用 interrupt() 暂停，之后用 Command(resume=...) 恢复。[3]

14.3 并发与幂等

  • 同一文档版本使用稳定 thread ID，防止重复创建独立运行。
  • 所有候选写入使用 content_hash + schema_version + extractor_version 作为幂等键。
  • 生产发布使用版本锁，确保同一 Schema 版本下原子写入。
  • 并行抽取的 State 字段必须定义 reducer，避免并发更新错误。

11. 架构结论

本项目最合适的形态不是“一个 Agent 自动生成知识图谱”，而是一个由 LangGraph 驱动的 受控自演化知识系统。

最终架构公式：
文档事件 → LangGraph 状态机 → 受限语义 Agent → 白名单工具 → 确定性验证 → 独立语义复核 → Policy Engine → Candidate/Shadow → 非 LLM Publisher → Production Knowledge Graph。
  1. 以 LangGraph Graph API 作为唯一编排和状态真源。
  2. Agent 只做语义判断，不获得生产写权限。
  3. 知识生产与 Schema 演化拆成两个子图和不同风险路径。
  4. 所有事实与本体变更都必须有文档证据、版本和运行记录。
  5. 用 Candidate/Production 隔离、Shadow Migration 和回归测试控制自动演化风险。
  6. 先实现单一子领域 MVP，再逐步扩大语料和本体覆盖范围。

代码与工程设计

12. 技术选型：为什么使用 LangGraph

LangGraph 的定位是面向长期、带状态 Agent 的低层编排运行时。其 Graph API 将系统拆成具名节点、边和共享状态， 适合把不确定的 LLM 语义节点嵌入确定性的治理流程。官方文档强调其持久化、durable execution、 human-in-the-loop 和流式执行能力。[1]

LangGraph 能力在本系统中的用途
StateGraph 显式定义文档处理、实体解析、Schema 演化和发布状态机。
Checkpointer 每一步保存快照，支持失败恢复、审批暂停、历史回放和 time travel。[2]
Conditional Edges 依据风险、证据质量和验证结果路由到发布、隔离、重试或候选积累。
Interrupt 高风险变更可暂停等待外部审批；即使日常不依赖人工，也保留治理断点。[3]
Subgraphs 将实体解析、本体演化、质量审计拆成可测试的独立子图。[4]
Streaming 实时输出节点更新、任务状态和调试事件，用于管理后台和观测。[5]
选择建议： 使用 LangGraph Graph API 作为主架构，因为本项目需要可视化拓扑、显式状态转换、 条件路由与子图组合。Functional API 可用于局部工具流程，但不应成为主控制面。

14. State 与数据契约

LangGraph 的共享 State 应存储可序列化的任务事实，不保存数据库连接、模型对象或不可重放的运行时资源。 节点只返回状态增量，外部副作用通过工具服务执行。

7.1 主状态模型

from typing import Annotated, Literal, TypedDict
from operator import add

class GraphState(TypedDict, total=False):
    run_id: str
    thread_id: str

    document_id: str
    document_version: int
    document_type: str
    domains: list[str]

    schema_version: str
    policy_version: str
    prompt_versions: dict[str, str]
    model_routes: dict[str, str]

    segments: list[dict]
    semantic_atoms: Annotated[list[dict], add]
    entity_decisions: Annotated[list[dict], add]
    claim_candidates: Annotated[list[dict], add]
    schema_proposals: Annotated[list[dict], add]

    validation_results: Annotated[list[dict], add]
    policy_decisions: Annotated[list[dict], add]
    warnings: Annotated[list[str], add]

    retry_count: int
    llm_call_count: int
    tool_call_count: int
    status: Literal[
        "running", "candidate", "published",
        "quarantined", "rejected", "failed"
    ]

7.2 关键设计原则

  • 输入中固定 schema_version、policy_version、Prompt 和模型路由，保证可重放。
  • 并行节点写同一字段时使用 reducer，避免并发状态覆盖。
  • 大文本、图片和向量不直接进入 State，仅保存对象存储 URI 和内容哈希。
  • 每个候选对象都带 document_id、版本、证据跨度和生成运行 ID。

15. 节点与 Agent 模块设计

节点 / Agent输入输出权限
Corpus Analyst 文档元信息、摘要、来源 文档类型、子领域、抽取配置、质量分数 只读
Semantic Extractor 片段、相关 Schema 子集、单位词典 Mention、Event、Measurement、Condition、Claim、Evidence 候选写
Entity Resolver Mention、Top-K 候选、别名、邻居 LINK / CREATE_CANDIDATE / AMBIGUOUS / REJECT 候选写
Schema Proposer 无法映射实例、聚类、关系模式 类型、关系、属性、合并或拆分提案 Schema 候选写
Semantic Critic 候选、原文证据、相关 Schema 支持、矛盾、过度推断、缺失条件 只读
Policy Node 全部验证信号 发布、保留、隔离、Shadow、拒绝 状态决策
Publisher 已批准对象与版本 生产写入回执 生产写；无 LLM
避免把所有节点都做成 Agent： 文档哈希、格式解析、单位换算、证据 offset 检查、循环检测、版本写入等必须使用确定性代码。 只有同义判断、概念归纳、实体消歧和 Claim 支持判断交给 LLM。

12.2 主图骨架

from langgraph.graph import StateGraph, START, END
from .state import GraphState
from .routing import route_after_validation, route_after_policy

def build_graph(checkpointer):
    g = StateGraph(GraphState)

    g.add_node("ingest", ingest_node)
    g.add_node("profile", profile_node)
    g.add_node("segment", segment_node)
    g.add_node("extract", extract_node)
    g.add_node("resolve", entity_resolution_subgraph)
    g.add_node("schema_gap", schema_evolution_subgraph)
    g.add_node("validate", validation_node)
    g.add_node("critic", semantic_critic_node)
    g.add_node("policy", policy_node)
    g.add_node("publish", publish_node)
    g.add_node("quarantine", quarantine_node)

    g.add_edge(START, "ingest")
    g.add_edge("ingest", "profile")
    g.add_edge("profile", "segment")
    g.add_edge("segment", "extract")
    g.add_edge("extract", "resolve")
    g.add_edge("resolve", "schema_gap")
    g.add_edge("schema_gap", "validate")

    g.add_conditional_edges(
        "validate",
        route_after_validation,
        {
            "critic": "critic",
            "quarantine": "quarantine",
            "reject": END,
        },
    )

    g.add_edge("critic", "policy")

    g.add_conditional_edges(
        "policy",
        route_after_policy,
        {
            "publish": "publish",
            "candidate": END,
            "shadow": "schema_gap",
            "quarantine": "quarantine",
            "reject": END,
        },
    )

    g.add_edge("publish", END)
    g.add_edge("quarantine", END)

    return g.compile(checkpointer=checkpointer)

12.4 Policy Engine

def decide_schema_action(signals: GovernanceSignals) -> PolicyDecision:
    if signals.deterministic_violations:
        return PolicyDecision(action="reject")

    if signals.evidence_coverage < 1.0:
        return PolicyDecision(action="retain_candidate")

    if signals.independent_document_count < 3:
        return PolicyDecision(action="retain_candidate")

    if not signals.critic_approved:
        return PolicyDecision(action="quarantine")

    if signals.risk_level == "high":
        return PolicyDecision(action="start_shadow_migration")

    if (
        signals.instance_coherence >= 0.85
        and signals.semantic_stability >= 0.85
        and signals.conflict_rate <= 0.05
    ):
        return PolicyDecision(action="promote_stable")

    return PolicyDecision(action="retain_candidate")

17. 测试、评估与可观测性

LangGraph 官方提供针对自定义图的测试模式；节点、路由和图状态应分别测试，而不是只测试最终答案。[6]

13.1 五类测试

Unit Tests

状态转换、规则、单位、证据 offset、循环检测。

Contract Tests

所有 Agent、工具和节点输出符合 Pydantic/JSON Schema。

Frozen Corpus

固定半导体文档，模型、Prompt 或 Schema 变化后重跑对比。

Metamorphic Tests

段落重排、格式转换、同义改写后，核心知识应保持稳定。

Failure Tests

模型超时、节点异常、重复执行和发布中断后的恢复能力。

Shadow Evaluation

新 Schema 在影子图上运行，不直接影响生产结果。
